# CLAUDE.md — system-design-prep

Staff/principal-level system design documentation set. Obsidian vault + git repo.
Inherits the workspace rules in `../../CLAUDE.md`; this file holds only what is specific to
**this** repo.

**Audience: staff and principal engineers.** Assume strong fundamentals. Never write a 101
explanation. The value here is trade-offs under constraints, failure modes, quantitative
reasoning, and where experienced engineers get the choice wrong — not definitions.

## Duplicate prevention — the hard rule

**Before creating any new file, read [interview-prep/topics/manifest.md](interview-prep/topics/manifest.md).**
Every topic has one canonical filename and a list of aliases that must never become their own
file. If a topic is not in the manifest, add it to the manifest *first*, then create the file.

Never end up with `caching.md` and `cache-strategies.md`. Never end up with a concept explained
in two files — one is canonical, the other links to it.

## Section contract — `type: topic` and `type: case`

Staff-level files use these headings, in this order. Sections that genuinely don't apply are
omitted, not padded.

| # | Heading | What it must carry |
|---|---|---|
| 1 | `Core concept` | 3–6 lines. Assumes strong fundamentals. No 101 |
| 2 | `Mechanics & internals` | The actual protocol/algorithm/data structure. No hand-waving |
| 3 | `Numbers that matter` | Latency budget, QPS ceilings, storage growth, cost. Real arithmetic |
| 4 | `Failure modes` | What breaks at scale, how it degrades, documented incidents |
| 5 | `Trade-offs vs alternatives` | X vs Y vs Z, and where staff engineers get this wrong |
| 6 | `Real-world examples` | Cited, specific systems and versions |
| 7 | `Staff-level follow-ups` | 3–5 multi-part probing questions. Never definitional |
| 8 | `See also` | Hand-written |
| 9 | `Referenced by` | Backlinks. Generated by the link pass, not hand-maintained |
| 10 | `Sources` | |

**Never write a literal `## Referenced by` line inside a code fence** anywhere in this repo:
`gen_backlinks.py` matches the heading textually and injects a backlink list into the example
block. That is why this contract is a table.

Case studies additionally keep the design skeleton (Clarify · Requirements · Estimates ·
API · Data model · Architecture · Scale & failure · Ops & cost) inside
`## Mechanics & internals` and `## Numbers that matter`.

**Completeness bar, not a word count.** Write as much as the topic needs to hit staff-level
depth; a file is done when every section above carries something a principal engineer didn't
already know. Case studies and comparison matrices are expected to run long. A short file is a
signal the topic is either thin or wrongly scoped — check the manifest.

## Diagrams

- **Mermaid only.** Plain text: git-diffable, reviewable in a PR, renders natively on GitHub,
  GitLab, Obsidian and VS Code with no plugin or export step.
- **Reuse [diagrams/components.md](interview-prep/diagrams/components.md)** — same shapes,
  same colours, same node naming. Do not invent a new visual language per file.
- **At least two diagram types per case file**: a `flowchart` for component layout **and** a
  `sequenceDiagram` for request flow. One generic box diagram per topic is the anti-pattern.
- Dotted arrows (`-.->`) always mean asynchronous. Labels carry the number that matters.

## Research rules

- **Cross-check 2–3 independent sources** before asserting a mechanism or a number. Do not
  inherit one blog author's framing.
- Prefer primary sources: papers, official docs, vendor engineering blogs, incident write-ups.
- Cite specific systems and versions. "Kafka" is weak; "Kafka 3.x with KRaft, `acks=all`,
  `min.insync.replicas=2`" is a claim.
- **Documented production incidents are gold** — a public postmortem beats any tutorial.
- Numbers get a source or the label "order of magnitude, verify before quoting".

## Links

- Relative only: `./file.md`, `../folder/file.md`. Lowercase-hyphenated anchors.
- Escape spaces as `%20` and parentheses as `%28` `%29` — legacy filenames contain both, and
  an unescaped `(` silently breaks the link on GitHub.
- Every file ends with **See also**, **Referenced by**, **Sources**.
- `Referenced by` is generated by the link pass. Do not hand-maintain it.

## Repo traps

| Trap | Rule |
|---|---|
| **Wikilinks are disabled** in this vault | Markdown links only. Legacy `[[...]]` links stay; add no more |
| Legacy filenames contain spaces and parentheses | Escape them; **do not rename legacy files** — it breaks inbound links |
| `interview-prep/10-resources/vendor/` | Upstream clones. Read-only, gitignored. Refresh with `fetch-references.sh` |
| `.obsidian/` | Gitignored; don't commit workspace state |
| New files | `kebab-case.md`, no spaces, listed in the manifest and in the folder's `index.md` |

## Git workflow

- **Never commit to `main`.** Branch per change: `type/scope-slug`
  (e.g. `docs/staff-level-restructure`).
- Conventional commits, imperative subject under ~72 chars. Body says **why**.
- One increment per branch; PR per branch; squash-merge; delete the branch.
- Docs changes still get the verification below before the commit claims done.

## Architecture Decision Records

Design decisions go in `docs/adr/`, numbered `NNNN-short-title.md`. Copy
[interview-prep/_templates/adr-template.md](interview-prep/_templates/adr-template.md).

**An ADR records *why*, at a moment in time. Nothing else.**

| # | Anti-pattern | Rule |
|---|---|---|
| 1 | Not writing ADRs at all | Decisions that live only in a head or a chat thread are gone in a month |
| 2 | ADR as developer documentation | ADRs say *why*, not *how*. Implementation belongs in READMEs |
| 3 | ADR as architecture overview | One decision at one time, not the system's shape. Use a diagram for that |
| 4 | Many decisions in one ADR | One decision per ADR so each can be superseded independently |
| 5 | Editing an ADR to change the decision | Append-only log. Write a new one, mark the old `Superseded by ADR-NNNN` |
| 6 | No alternatives recorded | List rejected options and why. Stops the same debate recurring |
| 7 | Hiding trade-offs | Record the costs: operational complexity, skill gaps, what this locks out |
| 8 | Letting AI make the trade-off | AI drafts and explores; the decision is a human's |
| 9 | Writing ADRs after the fact | Write while context is fresh; if reconstructed, say so |
| 10 | Writing and approving alone | Review like code. Shared understanding is most of the value |

Status: `Draft` → `Proposed` → `Accepted` | `Rejected` | `Superseded by ADR-NNNN`.

Source: [10 ADR anti-patterns — bool.dev](https://bool.dev/blog/detail/10-adr-antipatterns)

## Definition of done

- [ ] Topic exists in `topics/manifest.md` with canonical name + aliases
- [ ] Frontmatter complete, `updated` bumped
- [ ] Every section in the contract carries staff-level substance (no padding, no 101)
- [ ] ≥ 2 diagram types, reusing `components.md` vocabulary
- [ ] Numbers are real and sourced, or labelled as order-of-magnitude
- [ ] 2–3 sources cross-checked; incidents cited where they exist
- [ ] Link check run, **0 broken links**, output quoted
- [ ] Backlink pass run; `Referenced by` regenerated
- [ ] Folder `index.md` and the manifest updated
- [ ] Committed on a branch, never on `main`
